## P2d2-V1 — 100件より古い未完了purgeの再訪・手動回復が消える

- 根拠: JB-01「再訪時には最新の状態」、採用P2d-2-Dの失敗・再訪・回収再開。PurgeHistory自身も「直近90日の結果と、未完了の回収を表示」と案内する。新しいbulk要件ではない。
- 原因: `packages/core/src/adapters/libsql/repositories/purgeRepository.ts` の `list` は本人かつ「未完了 OR 90日内」を抽出した後、作成日時降順の `limit(100)` で切る。cursor/続き取得がない。
- 再現: 13:19:32、隔離実DBで本人の通常save→trash→requestを実行し、回収failedを保持。後続100件のsucceeded intentを同じ永続行契約でseedする。後続は通常の単一purge100回が作る一覧集合と等価で、production大量作成はしていない。
- 実際: `listNotePurges` の返却100件はすべて後続結果。旧failedはDBに残るが返却にない。独立assert `expected true / received false`。新しさだけで未完了が消える。
- 期待: 本人が再訪して未完了状態を取得し、手動回復へ進める。固定limitの数を増やすだけを合格条件にはしない。
- 別導線: `/trash` と `/notes/jobs` は同じPurgeHistory。ID指定読取のpresentation入口はなく、手動retryは返却itemにあるボタンのみ。IDを既に知る内部呼出なら `retryNotePurge` は本人再試行できるが、再訪利用者がIDを回収するUIではない。ImportTickerも同じ限定listを読む。返却がすべてsucceededならPurgeHistoryのpollも終了する。
- 影響: P2d-2-D、共有P2d-1-Dの表示・再訪。不変のworkerは古いfailedも引き続き自動再試行し、容量行・intentも保持する。物理消去不能、容量先行解放、他人への漏洩とは認定しない。
- 正常対: 本体の新自己noteではfailedを表示→Spaceで手動retry、30秒後の自動retryを同画面で検知、別画面再訪、応答喪失後の再取得が成功した。少数時の正常対はV1とは別に保持する。

## コード・採用根拠の境界

- 入力はtyped transportのnote/operation/intentのみ。回収keyはDB provenanceから列挙し、HTML/同名を権限にしない。purging/version/job失効/intent/capture/pin解除は同UoW、本文revisionを増やさない。
- import upload、conversion、media upload、reference workerの全実処理をwithObjectOwnerで包み、second put/publish/commit/finallyまでactive ownershipを維持する。production DIはCoordinatedObjectStorage一系統。通常media GC/import cleanup/reference finally/orphan cleanupも同removeClaimedを通る。
- removeはUoW外。claimと同keyqueue、publish前再確認、削除tokenとpurge lease再確認を組み合わせる。容量は既存original/asset/予約/reference所有行へ残り、削除完了・全writer収束前に0にしない。stale reference writtenのupsert復活拒否、未回収/activewriterのjob pruning除外を確認。
- process-ownerはroot単位の独占と既知PID終了確認。期限/lease/最初の不存在はwriter終了の証拠でない。生存/生存不明/PID再利用を強奪しない。複数host/共有FSの並行writer保証を採用していない。
- source/safe重複は一予約、committed reference-object/assetは一容量所有。共有companionは他note関係、未seal、受理予約、利用writerを確認し最後に回収する。通常7日GCのeligibilityは今回変更なし。
- snapshotは本人/元ID/元日時/最小terminal結果のみ。削除済み変換retryとpurge回収retryを分離し、本文・CSS・binaryを90日保持する代替にはしていない。90日cutoffと未完了intentの保持を分離する。ただしその未完了をUIへ届かせる点はV1不合格。
- public client API/同URL共有resource queueとDrizzle UoWを維持。lock差はclient/core0.18.0、Drizzle peer identityだけ。native0.5.29/hrana0.10.0等不変。手製BEGIN/private API/製品forcedGCなし。
- 公開[Client](https://tursodatabase.github.io/libsql-client-ts/interfaces/Client.html)・[Transaction](https://tursodatabase.github.io/libsql-client-ts/interfaces/Transaction.html)契約と[registry 0.18.0](https://registry.npmjs.org/@libsql/client/0.18.0)を確認。gitHead `9496c782af413f6380235c7f5d0c97b5371f49b7`、tgz SHA `908ffc033249e2b77b230f02d0b0884b5cfb9aa9e7a91b3937a4e04ede02087a`、cache sqlite3 SHA `453ca868a8f8e9d87362e97ef1d2aabf2039b6afd82b92409c4fee5a5b5a98a0` が公式tarballと一致。remote実接続は未検証。
