## 修正と検証範囲

### 新規ローカル環境

`tests/setup.ts` は各 test file ごとに `~/.local/share/hollow/verification/suite-*` を mode 0700 で作成する。DB / objects / tmp / fixture keys はこの新規 root 内に置く。既存の fixture 環境変数を専用パスで上書きし、資格情報や秘密 env を読み込まない。キーは固定の synthetic 32-byte 値を mode 0600 / exclusive creation で生成する。成功した test file の生成物は終了時に削除し、失敗した test file はログにパスを記録して保持する。削除対象は自分で作った root のみ。

Node integration の通常コマンドは従来の include 範囲を維持し、local-format の 2 files を五つの project として明示的に実行する。`formats-app` 9、`formats-app-c` 9、`formats-native` 7、`formats-native-d` 2、`formats-native-e` 2 の全 29 cases を実行する。元の group 条件に従う正常 / 異常 / native ownership シナリオを残す。baseline の `HOLLOW_S4_GROUP=app` のみという実行条件を解消する。

Native bootstrap は公開 `tests/nativeFormatsBootstrap.mjs` へ移し、checkout / Node executable / fixture root の絶対固定を解消した。実 child と grandchild の生存、親子所有、physical exit、同じ DB の recovery、checkpoint の確認を保持する。Drive backup predecessor も公開 `tests/driveBackupPredecessor.mjs` から実 adapter / source handle / IPC child を動かし、実サービスへ向かう request は loopback HTTP fixture へ注入する。

### 現在の schema / port 契約

- accounts / sessions の positional raw INSERT を column 名付きへ修正。追加 column に依存せず現 schema の defaults / constraints を通す。
- schema migration 総数は 44。0041 専用 migration テストは 0040 までの schema に raw SQL / Drizzle insert で既存行を作り、0041 だけを適用する。将来 schema を参照する現 UoW を移行前 DB へ使わない。4 target states、3 accounts、backup requests / jobs / transfer / record の保存、copy / trigger / FK fault の rollback、guards の assertion を維持する。
- backup fixture の `isCurrent` / regeneration lease `held` / `cancelPending` を現在の必須契約に揃える。
- llmPreparation / PdfPersistence は source-origin / binding / memory / receipt の現 schema 値を明示する。
- InputStage は local-v2 ownership を渡し、PDF classifier と PDF-page adapter を実 NodeRegenerationMemory に注入する。成功 receipt の closed、課金上限で拒否された未取得 receipt の null、所有 / cleanup / cancellation の assertion を維持する。
- accounts.save は insert-only 契約なので、既存 account の再検証 fixture は正しい markVerified を使う。

### Unit / native process

Vitest 4 の Worker mock を constructible class とし、実 Worker prototype の契約を維持する。非同期 native reserve の後で生成される image / PDF child は microtask 完了後に assert する。runtime manifest は version 3 / leased-local-v2 を期待する。

`tests/resolveTsImports.mjs` は Node 22 の型変換で動かす fixture child の相対 extensionless `.ts` import を解決する。既存解決を先に試し、ERR_MODULE_NOT_FOUND の相対・拡張子なし・file parent に限り `.ts` を試す。製品の resolver / loader は変更しない。

### Bulk isolation / timeout / worker bundle

Bulk backup の各 scenario は新規 DB と 510 notes / 513 originals を持つ。共有 fixture で前 scenario の cleanup が original を purge / replace し、後 scenario の期待値と実 DB がずれていた。scenario 名をその独立性に揃え、DB label `application-vN` を二桁にも対応させた。失敗による後続 context.skip を外し、各 case を実行する。pending cancellation / purge の case は purging lifecycle を seed し、現在の purge 前提と cancellation fence の順序を両方 assert する。

最大境界の public discovery case は 51 notes × 50 tags の seed、正規化拡張 query、実 worker と HTTP、複数ページ / cursor の完全な assertions を維持し、case 自体の timeout を 30 秒にする。製品 search の 3 秒 budget は変更しない。高い既定並列数で他 files が DB seed / native child を実行している full suite では HTTP 503 に到達し、個別実行は HTTP 200 で成功したため、Node pool は同時 2 files に限定する。入力件数、assertion、対象、製品 deadline を緩和しない。

Fresh checkout は exportFlow の既存 dist 暗黙依存も検出した。suite の beforeAll が製品と同じ Node 22 / ESM / css-tree external / createRequire banner で実 export worker を専用 root 内に build し、実 Worker へ渡す。依存解決用 node_modules link は現在 checkout 内だけを参照する。30 cases の出力、HTTP status、権限、取消、spool ownership 等を保持し、通常 pnpm test と個別 suite が事前 build に依存しない。

## Fresh checkout 再実行手順

新規の通常 git checkout を persistent verification directory に作る。今回の検証では、既存 git ls-files の公開 source と新規 tests を投影し、`.goal-implement/` と `spec/` を除外した新規 directory を git init / 明示的 index 登録して使った。旧 archive や保全資料はコピーも読み取りも行わない。checkout は git 管理される source と commit 済み tests を含める。Nix が source tree として未管理 node_modules を全コピーしないよう、git checkout のまま実行する。

以下は checkout root で、PATH / HOME のみを引き継いだ環境に入り、TMPDIR を新規 persistent root に作った `tmp` に設定して実行する。WRANGLER_SEND_METRICS=false、CI=true。`pnpm install` の offline は既存 pnpm store があるこの環境の再現条件で、未取得環境では通常の frozen-lockfile install を使う。

```sh
nix develop
pnpm install --offline --frozen-lockfile --ignore-scripts
pnpm cf:types
node -p 'JSON.stringify({node:process.version,unicode:process.versions.unicode,execPath:process.execPath})'
pnpm exec node -p 'JSON.stringify({node:process.version,unicode:process.versions.unicode,execPath:process.execPath})'
pnpm typecheck && pnpm lint:fix && pnpm format
pnpm lint
pnpm format:check
pnpm test
pnpm build
```

通常 pnpm test は unit → Node integration → Cloudflare integration の順。Node / CF の db:generate は tracked schema に変更がないことを確認する。CF は Workers isolate + Miniflare D1 のローカル binding のみで、実 Cloudflare API や資格情報を使わない。
