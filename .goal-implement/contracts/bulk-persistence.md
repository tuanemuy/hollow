# P3eの永続受理とcommand接続

[固定D2への接続案と末尾補足](../phases/P3e-plan.md)の親・固定target・attempt・move holding receiptの4表構成を採用する。同parentは1running、初回は固定ordinal、retryは受付generationとordinalの順に実行する。単一tag/move/trashのapplication command coreを現在認可と同UoWのまま共用し、子変更・結果・receiptを一つのcommitにする。workerは永続actorの現在account/policyを検査し、元sessionやcookieを保存しない。既存の物理writer/回収provenanceはbatch履歴に移さない。

同parentの成功receiptで導出できるのは2scopeのholdingと、同じ純粋式で計算する移管増減額だけである。後続note自身のversion/所有世代/resourceRevision/固定資源内訳/tag対応、scope名/membership、bundle content/bytesは元確認値のまま厳密比較する。apply後は元source/destinationを明示した有限bundleState readで実before/afterを同Tx取得する。初回の合計説明は固定順の仮想holding理由count遷移で同bundleを一回課算し、全件成功想定と各子の現在quota検査を区別する。

holding sequenceはbundleありの成功moveだけで進め、0Bでもedgeを残す。bundleなし成功はholdingSequence:nullとする。receiptは最大500、同parentの連続prefixだけをpruneし、prunedThroughと現在sequenceの間のcoverageを同bundle抽出前に照合する。必要edge欠落・古いbaseは拒否する。失敗子retryは固定対象/設定の新previewと同Tx取得baseを起点にし、成功/取消済みを再実行しない。未終端parentが依存する最小edgeは保持し、表示用title/旧attempt詳細の90日寿命や物理回収負債と混同しない。

明示新規tag名は不変intentと一度だけ確定するbindingを分ける。accept時に同名IDがあれば固定し、なければ最初の成功子のensure/attach・親binding・結果を同Txで確定する。失敗時は新tagもrollbackする。resolved後は固定IDだけを使い、外部delete/merge後の同名別IDやfailed retryで差し替えない。未resolvedの同名外部create競合は既存一意制約で収束し、nameから結果identityを逆引きしない。

previewは50件ずつ最大500の確認値を集め、ページ間の同bundle確認状態が異なれば再確認する。acceptは表示した対象外/実行集合を現在認可で再照合し、同内容requestだけを同親へ収束する。membership edit-lossとnote trash/purgingの既存同Tx入口へ未終端子の自動取消を接続し、batch自身のtrash実行attemptは除く。通常親取消のrunning結果保持と、外部失効後の旧attempt採用拒否を分ける。取消は理由なし、通常条件違いは理由あり失敗とする。500確認payload/受理SQL量・worker leaseの運用値は正式実装時に狭く確認し、未測定の成立を合格としない。

batch workerの初期運用値はlease60秒・周期2秒・1wake最大20子とする。同parent1runningを保ち、停止時は新規claimを止め現在Txの終了を待つ。leaseはdeadclaim回復用で、I/Oの強制終了期限や全件完了時間ではない。中断したrunningは期限後にBATCH_INTERRUPTEDのfailedへ収束し、利用者の明示retryで新attemptを作る。同attemptの自動再実行は行わず、未claim queuedは通常の初回実行へ進む。target試行番号は初回1・新attempt時だけ+1とし、親generationと分ける。成功commit後のack喪失は結果再読取だけで番号を増やさない。期限後の旧token不採用、別instanceの回収、現在policyと試行番号を確認し、既存の他種類jobの回復方式は変更しない。最大確認payloadと受理SQL量の成立は別に測定する。

通知watchは現在本人の最大50一意parent IDを同UoWで照会し、既存BatchRepository.summaryからBatchViewだけを返す。子pageを通知のために取得しない。activityの親数・親page50と用途を分け、page消失・未知/別人/期限外を成功終端としない。既観測のcontextと旧success/catch/finallyを検査し、実終端遷移だけを通知する。

BatchSelectionProviderはRoot Outlet外へ独立配置し、actor表示guardは既存のvalidated route-contextから得る。BrowseProviderと単一paletteの配置は変えない。未送信selectionは一覧離脱/reload/filter・scope・zone変更で解除し、受理中request・応答不明・本人通知の寿命と分ける。actor変更と旧route応答でdialog復活・新selection消去・自動navigate/再送を起こさず、client actorをserver認可に使わない。

ZIP受付の成功処理は、送信時の選択を識別するcompletion ticketを使う。共有SelectionContextのcompletionTicket/clearIfCurrentはcontext key/epochとprovider内の同期revisionを照合し、change/clearごとにrevisionを進める。同actor/filterでAからBへ、又はA→B→Aへ選び直した後も、旧受付応答は現在の選択を消さない。選択が変わらない通常受付だけを解除する。既存BatchContextのguardと、非同期全体選択照会のticket/valid契約は維持し、serverの固定対象・receipt・ACK不明時の明示再送は変更しない。

一括trashは明示cancelProcessingと現在version/処理確認値を固定する。同意した処理は既存coreで通常取消してtrashへ進め、同意不足は対象別失敗、後発/入替は再確認にする。参照jobはnote.version不変でも新IDへ入れ替わるため、batch expectedだけに現在queued/runningの種別とIDを正規順でhashしたprocessingFingerprintを持たせる。確認/受理/子実行の同UoWで現在集合と照合し、同IDのqueued→running/進捗は許容する。fingerprintは確認値であり権限tokenやTTLではない。単一trash API・既存job方式・schemaは変えず、同bool/versionの入替再現と修正後の拒否・同ID正常進行・rollback/兄弟継続を分けて検証する。
