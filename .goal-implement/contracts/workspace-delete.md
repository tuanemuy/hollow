# P3fのワークスペース削除

[P3f共有契約案](../phases/P3f-contract.md)を基に、不可逆なアクセス失効と物理回収の完了を分離する。削除時点の現在ownerと現在の保存名に一致する確認入力を同UoWで検査する。確認中の改名は再確認とし、タグの正規化を借用しない。削除後は個人文脈へ移り、note・tag・membership・公開ページの削除と事前の移動導線、取消不可を明示する。受理を物理削除完了として表示しない。

第一候補は、WSの不可逆fenceと削除intentを受理し、閉じた現在所有集合を有限SQLで回収へ入れる方式とする。全current read/write/register/publish/結果採用・未bind資源が同じscope失効を守ることが前提であり、現実装での成立は未検証である。成立しない入口があれば接続を先行するか、全note同期更新との比較をManagerへ返す。500件の全体上限、本文の全件JS配列、新しい確認期限は加えない。

削除と移動は現在scopeを同UoWで照合する。先に移出したnoteと資源は新scopeへ残し、先に移入したnoteは削除対象になる。削除受理後の移入・移出・新規bindは拒否する。creator/uploader/元jobのWSを現在所有の代わりにせず、中立公開identity/tokenや他scopeの共有companionを巻き込まない。

回収は永続削除intentと対象所有に束縛した専用の内部入口から既存purge/claimへ接続する。失効したmembershipや任意の認可bypassを根拠にしない。通常jobは取消して遅い結果を拒否し、不可逆fence済みのpurge/cleanupと削除自身の回収は継続する。current icon pointer解除、招待/継続認証/未送信配送の失効を受理境界へ接続し、writer終了と実removeまでは資源provenance/chargeを残す。

回収専用状態は削除scope ID・intent/世代・未回収claim/charge参照・再開位置に限定する。membership/招待秘密/本文/期限外jobを回収権限のために保持しない。[現行接続案](../phases/P3f-plan.md)の同じWS IDを持つdeleted縮小行と、別の削除intent・本人receiptを採用する。課算先を別IDへ移さず、slugは現行の予約を維持して再利用を有効にしない。active行の必須profile制約とdeleted行の縮小を型とDBで分け、新migrationのcloneでFK/trigger/既存行の保全を確認する。安全に移行できなければ専用tombstoneとの比較へ戻る。

新しい削除操作の本人receiptは受理から既存JBの90日とし、未回収intent/対象対応は回収完了まで別に保持する。元の変換・参照・batch履歴の作成日時と90日を削除時点から延長しない。期限外の本人名/request/digestを回収権限のために残さず、期限外再送を新しい削除実行にしない。admission前に既存purgeがnoteを消す競合は、purge完了の同Txで削除intentへの一意対応を確保する。削除受理より前のpurgeを時刻や旧workspaceIdから後付けで対象にしない。

writerのbegin/register/publishと最終結果採用は同Txのcurrent scopeを検査する。bound資源は現在note所有、未bind資源だけはdraft/import admission所有を使う。P3eの取消は未終端attemptと現在note所属・有効な移入先に限定し、親の旧sourceだけで移動済みnoteや成功receiptを変更しない。未bind回収は削除intentに束縛した有限処理とし、通常GCの期限を偽装しない。これらは採用契約であり、P3e固定候補への再照合と全入口の実検証はP3fに残る。

P3fはnullable profileとactive/deletedのDB CHECK、および削除intent・note/purge対応・本人request receiptの3表を追加する。PurgeIntentにはworkspace-deletion原因とintent IDを型で結び付け、finish同Txで対応の一意確定と完了を行う。UoW内の専用削除repositoryが受理/本人receipt/claim/有限候補/対応/metadata回収/完了判定を担う。汎用SQLや認可bypassを内側へ公開しない。

初期運用値はclaim lease60秒・周期2秒・1wake最大20intent-step、note admissionは1step最大50 IDとする。総対象数の上限や全本文読取を追加しない。leaseは停止writerの回収完了や物理I/Oの強制期限ではない。旧token/再claim/cursorとfinish競合・既purge共有の再開、失敗時の再試行間隔を確認する。実測で不成立なら根拠と代案を返し、要件の対象件数を縮めない。

本人receiptはactor限定・元受理から90日の50件keyset pageで再訪できる。request照会のnullは未受理の証明ではなく不明を保持する。reload後のACK不明を追える最小actor/request識別子をsessionStorageに保持し、形式検査・保存失敗の代替・確定後除去を行う。保存値を認可や現在WS情報として信頼せず、自動POST・新request置換・旧actorの遷移を行わない。delayedはintent.lastFailureに基づく再試行待ちであり、経過時間だけの失敗判定ではない。

本人履歴DTOはserver session由来actorIdを持ち、initial/current actorと追加pageのactor・request epochを照合して表示する。client actorIdを認可入力にしない。rootの本人向け未確認要求はpathnameだけで隠さず、削除済み404でも同requestを照会できる。旧loaderや旧success/catch/finallyで別actorの結果を表示しない。

P4は削除WSに残るnoteの公開/限定URLとartifact取得も現在scope失効で拒否する。P5は関連backupを取消すが、個人Google連携の解除や既存Driveファイル削除を伴わない。公開・backupの実接続は後続条件に残す。作成枠が空いても物理回収負債は消えず、tombstoneだけでは作成/削除反復のdisk増加を制限できない。これは追加観察として保持し、新quotaや作成禁止を採用しない。
