# P4 の URL・書き出し共有契約案

## 判断の要約

- Q1 は中立の note 識別子と独立した公開 URL 世代を推奨する。所有移動と URL 更新を分ければ、OR-12 と SH-07 は両立する。「著者」を既知 creator と解釈するか、WS-07 の失効対象を WS 公開ページに限定するかは Manager 判断とする。
- Q2 は生成時の不変 snapshot、現在の内容一致、現在の閲覧認可を分ける。未変更の snapshot は PDF 24 時間・ZIP 7 日の間、同じ生成物を再取得する。変更後の古い生成物は渡さず、明示した新しい要求へ案内する案を推奨する。
- 完成後に一部の閲覧権限を失った ZIP は、そのまま渡さない。「取得可能な対象から新しく作成」を明示操作として提供する。生成中の対象削除は EX-02 に従い、その対象だけ除外して継続する。
- URL の具体的な文字列、schema、暗号方式、renderer、保持期限の起点、ticket・rate・resource の新しい数値は決めない。独立 Verifier の受入項目も追加しない。

## Q1: URL と所有移動

### 真の未指定点

OR-12 は「移動」という操作、SH-07 は「著者 handle 変更」という別の操作に条件を付けている。移動で note URL を組み立て直さなければ、両者は論理的に矛盾しない。

SH-07 の「著者」は公開ページに表示する人物を指す。OR-11 の作成者と同じ creator と読む案が自然だが、原文に厳密な同一性定義はない。現在 owner、最初の公開者、最新編集者、uploader と同じ人物とする根拠もない。既知 creator / unknown / 退会済みの区別を保持し、URL のために人物を補わない。

WS-07 は「公開ページのスラッグ」を編集する節である。DS の URL 表も WS 公開ページを `/w/スラッグ` と定める一方、note の公開 URL 形式は定めない。この文脈では「旧 URL」を WS 公開ページに限定する解釈が最小である。すべての WS 所有 note の URL も変える解釈は可能だが、追加の利用者可視の挙動になる。

### 推奨する最小契約（未採用）

URL の役割を次の四つに分ける。例示した `/p/N/G` は説明用であり、route の採用ではない。

| URL | 識別 / 失効の契約 |
| --- | --- |
| アプリ note URL | 現在の所有 scope と note。移動後は新しい文脈へ接続する |
| 個人 / WS 公開ページ | 現在の handle / slug。変更前のページ URL は転送せず not found |
| note 公開 URL | 中立 note anchor `N` と公開 URL 世代 `G`。現在 scope や人物名を毎回組み立てに使わない |
| 限定共有 URL | note の現在共有 token。公開 URL 世代、handle、slug と独立。失効・復活は SH-01/04 の条件に従う |

公開 URL は現在の公開状態・lifecycle と現在の `G` を確認して本文へ接続する。世代なしの note anchor だけで旧 URL 失効を迂回する公開入口を設けない。旧世代から新世代へ redirect すると「失効」にならないため、旧世代は not found とする。canonical と検索結果は現在の URL を使う。

公開操作の handle / slug は現在所有 scope の前提条件であり、永続的な URL 発行者ではない。OR-12 の移動は公開へ変更する操作ではない。公開済み note を handle / slug 未設定の所属先へ移しても、移動拒否や自動非公開化を追加しない。公開状態と URL を保持し、移動後に改めて非公開から公開へ変更する場合は、その時点の SH-01 の前提を確認する。この読み分けは採用する仮定として明記する。

SH-07 の著者を既知 creator と採用する場合、その人物の公開 handle の実変更で、その人物が作成した存続 note の公開 URL 世代を更新する。所有移動では creator も世代も変えない。unknown は更新対象の人物を推定しない。退会は handle 変更と同じ操作にはせず、存続 WS note の URL を保つ。

この解釈では、WS を離れた creator の後日の handle 変更も、その人が作成した WS note の公開 URL を変える。これは SH-07 の人物解釈から生じる効果であり、membership 失効による共有停止ではない。公開状態と限定 token は変えない。それでも WS に残る公開 URL への影響は利用者可視の選択なので、Manager が明示的に採否を決める。

handle の初回設定・設定解除も「変更」に含めるかは未決。推奨は既存値からの変更・解除を失効対象にし、未設定から初めて設定するだけでは既存 WS note の URL を変えない解釈である。SH-01 は handle がない WS creator を禁じていないため、この対を公開前提へ混ぜない。

WS slug の変更は WS 公開ページ URL だけを失効させ、note の中立 URL と限定 token は保持する案を推奨する。WS 自体が非公開でも公開 note は成立するため、note URL の有効性を WS 公開ページの存在へ依存させない。

### 個人 → WS → 別 WS → 個人の例

A が作った note N を、A 個人から WS-X、WS-Y、B 個人へ順に移す。各移動の実行者は、その時点の移動元 / 移動先の編集権限を持つ。B が最後の移動を実行する。A の公開 handle は `aki`、B は `bob`、WS-X / Y の slug は `design` / `research` とする。

| 操作 | 所有 / timeline | 公開 note URL | 著者 / 限定共有 |
| --- | --- | --- | --- |
| A 個人で公開する | A 個人 / A の公開一覧 | `/p/N/G1` | creator A / token T |
| WS-X へ移す | X / 公開 WS ページには X が公開のとき掲載 | 同じ G1 | A / 同じ T |
| WS-Y へ移す | Y / X の一覧から除く | 同じ G1 | A / 同じ T |
| B 個人へ移す | B 個人 / B の一覧 | 同じ G1 | A / 同じ T |
| A が `aki` → `aki2` に変更する | B 個人のまま | G1 は失効、G2 を使う | A のリンク先は新 handle / 同じ T |
| B が `bob` → `bob2` に変更する | B の公開ページ URL が変わる | N の creator は A なので G2 を保持 | A / 同じ T |
| 元 WS-X / Y の slug を変更する | 各 WS 公開ページだけが変わる | G2 を保持 | A / 同じ T |

A の著者リンク先の公開ページに N が並ばなくても矛盾しない。著者リンクは人物へのリンク、公開一覧は現在の所有 note の集合だからである。

WS-Y 所有中にその WS の slug を変更する場合も、推奨案では WS 公開ページのみが失効し、N の URL は変わらない。現在所有 WS の slug 変更で note 世代も更新する代案を選ぶ場合は、この一行だけが別の結果になる。移動元の WS の後日の slug 変更は、いずれの案でも移動済み note を失効させない。

### 削除と未知の著者

- A が退会した時点で N が WS に残っていれば、AC-09 に従い note と公開 / 限定 URL を保持する。作者は「退会した利用者」、著者の個人ページは not found とする。退会した A の handle を後で別人が取得しても、N をその別人に結び付けない。
- A が退会した時点で N が B 個人所有なら、A の個人所有 note ではないため N は残る。同じ退会済み作者表示を使う解釈を提案する。B 個人所有の N は B の退会時に削除し、両 URL を失効させる。
- WS-X を削除した時点で N が Y または B へ移動済みなら、N は X の削除対象ではない。元発行 namespace の削除を理由に N の URL を巻き込まない。N がその時点で X 所有なら WS-10 の削除対象となり、公開 / 限定 URL は not found になる。
- creator unknown の旧 note は、現在所有 scope の公開前提を満たせば中立 URL を発行できる。著者は「作成者不明」、人物リンクは出さない。owner / uploader を作者に補うことも、公開できない旧 note にすることもしない。
- handle / slug の文字列を別主体が取得しても、note anchor の所属や creator を名前一致で付け替えない。公開ページの文字列再利用可否そのものは今回の提案対象外である。

### 代案と採否の境界

| 案 | 適合 / 残る問題 |
| --- | --- |
| 中立 URL ＋ creator handle 変更で独立世代更新（推奨） | 移動不変、unknown、元主体削除を両立する。元 creator が WS 公開 URL を後から変えられる意味を承認する必要がある |
| 現在 owner の handle / slug を毎回 note URL に使う | 素直な namespace だが移動で変わり、OR-12 に反する。旧 alias を残すだけでは変更時失効との範囲が再び未決になる |
| 初回公開 namespace を固定する | 移動は保てる。元個人 / WS の削除後もその namespace を残す必要があり、削除対象と著者を混同しやすい。SH-07 の creator 変更にも別契約が必要 |
| creator handle を note URL に直接使う | 既知 creator の変更は説明できるが、handle のない WS creator、unknown、退会を別 route で補う必要がある。公開操作に creator handle を要求する追加制約は採用しない |
| 世代なしの永久 note URL | 移動には適するが、SH-07 の旧 note URL 失効を満たさない。SH-07 を著者ページだけと読み替えるのは明示した要件解釈変更になる |

P3d の移動へ必要な共有条件は「公開 identity / token / creator を移動で書き換えない」までである。具体 URL 発行や公開 policy を P3d の新しい完成条件にしない。

## Q2: 生成物の内容・認可・寿命

### 分離する identity（未採用）

| 対象 | 必要な区別 |
| --- | --- |
| 生成入力 snapshot | note ID、出力形式と設定、title / filename、正本 HTML、styleMode、出力に使う style / 取得済み媒体の正確な内容。出力に含む他の metadata も含める |
| 実生成 artifact | 上記 snapshot から確定した一つの不変生成物と、その生成物自身の保持期限 |
| 要求 / job | 実行者、元の対象集合、子結果、試行・取消。共有実生成物を参照しても、別人の履歴を見せない |
| 閲覧根拠 | 現在の session / ownership / membership、または現在の public 入口、または現在の token と password 通過状態。ticket は要求への束縛を補うだけ |

内容 identity を note.version や updatedAt だけにしない。採用済み OR-12 の移動は note.version を進めるが、本文版や更新日時を変えない。反対に出力 style・素材の変更は本文文字列だけでは識別できない。ここでは一致条件だけを決め、hash や保存 schema は詳細設計へ残す。

出力に現在含める要素が同じであれば、所有移動だけで生成し直す必要はない。移動後の閲覧認可は別に再評価する。snapshot の保持は公開閲覧者へ過去版 / 原本の読取権限を付与しない。

### 推奨する再取得契約（未採用）

PDF / ZIP は生成時の snapshot を固定し、生成の途中で別版の HTML や素材を混ぜない。同じ snapshot が現在の出力対象と一致し、現在の閲覧根拠が成立し、保持期限内なら、生成し直さず同じ artifact を返す。再取得で保持期限を延長しない。

本文・title・style などが変わって snapshot が一致しなくなった場合、古い artifact は現在の download として渡さない。現在も閲覧できる利用者には「内容が更新されています。最新の内容で作成」を示し、元の download 操作から新しく要求する。古い artifact の完了日時や元の job 結果を新しい結果へ無言で置き換えない。これは 24 時間 / 7 日の保持保証に対する「内容変更後」の明示した解釈であり、原文に追加済みとは扱わない。

適用を匿名だけに分けず、アプリ内 PDF / ZIP にも同じ現在内容一致を使う案を推奨する。アプリ内だけ古い snapshot を渡す案には、保持 20 版を越えた snapshot や取得当時と異なる membership をどの権限で読めるかという別の履歴契約が必要になる。

次の例は現在認可だけでは不足する理由を示す。

1. 所有者が非公開 note の秘密を含む本文 V1 で PDF を作る。
2. 秘密を除いた V2 に保存し、その note を公開する。
3. 匿名閲覧者が公開 note の PDF を要求する。
4. 現在 public という判定だけで V1 の cache を返すと、匿名閲覧者が一度も閲覧できなかった本文を渡す。V2 と artifact の内容 identity の一致を別に確認すれば、この経路を閉じられる。

### PDF の時系列と重複排除

| 時点 | 推奨する結果 |
| --- | --- |
| T0: N / snapshot S1 の生成を要求 | S1 を固定し、単一の note 実生成へ接続する |
| T1: 本文 / title / style を S2 に更新 | 実行中 S1 を S2 と混ぜない |
| T2: 別の閲覧者が同じ N の PDF を要求 | EX-04 に従い、新しい並列実生成を開始せず、実行中処理の終端を待つ。現在読める本文は S2 であることを保持する |
| T3: S1 の生成が完了 | 現在 S2 と不一致なので S1 を渡さない。現在認可がある各要求者へ更新とやり直しを案内する。認可も失った要求者へ内容変更を漏らさず not found |
| T4: 明示的に操作をやり直す | S2 の生成または一致する保持 artifact を使う。同時のやり直しも同じ実生成へ合流する |
| T5: S2 が未変更で生成完了 | 各要求者自身の現在認可と ticket を確認し、同じ結果を受け取る |
| T6: ticket だけが期限切れ | 操作やり直しで新 ticket を取得する。S2 が一致し 24 時間内なら PDF を再生成しない |

EX-04 の「同じ結果」を無条件に古い本文へ適用するかは原文未指定である。推奨案は「未変更なら同じ結果、変更後は同じ実行の終端を待って更新を明示」と解釈する。自動的に最新版へ追従する方式は、連続編集で完了しない可能性と要求者ごとの対象版が曖昧になるため、最小案にはしない。

実生成への合流と job 履歴の所有は別である。A と B が同じ PDF の計算結果を共有しても、A の job ID / 履歴を B に渡さない。匿名は自分の ticket で許された画面内進捗だけを受け取り、既存の signed-in job を列挙できない。実生成の最初の要求者が誰かは、他の要求者の閲覧許可にならない。各要求者の失効 / 取消は、その要求者への受取を止める契約とする。共有 worker の継続・停止の具体方式は詳細設計へ残す。

### ZIP の時系列と部分失効

ZIP は対象ごとの snapshot と、それぞれの成功 / 失敗 / 除外の内訳を持つ生成物として扱う。完成済み ZIP の一部だけを HTTP 応答中に隠すことはできない。含有ファイル全体を対象に現在の認可と内容一致を確認してから渡す。

| 状態変化 | 推奨する結果 |
| --- | --- |
| 生成中に B が削除 / trash / 閲覧不可になる | B を除外し、正当な A / C を継続する。EX-02 の部分成功と失敗 / 除外一覧を維持する |
| 生成中に B の本文等が変わる | B の snapshot を無言で最新版に差し替えず、内容更新としてその対象を失敗 / 除外にする。他対象を継続し、最新 B は明示した再要求へ案内する |
| A / B / C の完成後、B が閲覧不可になる | 既存 ZIP 全体の download は止める。「取得できる対象で新しく作成」を示し、A / C の新要求を利用者が確定する。全対象が不可なら新生成しない |
| B は private になったが実行者に現在 membership がある | その実行者の app 閲覧根拠は残る。private 化だけを ZIP 拒否の理由にしない |
| 実行者が除名されたが B は現在 public | 完成済み本人 ZIP の受取では B の現在 public という独立根拠も評価し、除名だけで一律に拒否しない。他の含有対象も現在読め、内容が一致する必要がある。進行中 job の取消は JB-03 と別に扱う |
| 完成後に B の title / HTML / style だけが変わる | 既存 ZIP と現在内容が不一致であることを示し、最新の対象集合で新要求する。古い ZIP を最新として渡さない |
| 7 日経過、job は 90 日以内 | artifact は期限切れ、本人の履歴と再実行導線は残る。履歴の存在で生成物保持を延長しない |

完成後の回復は、完了済み job の失敗子 retry を偽装せず、EX-03 / JB-02 の「元の操作をやり直す」新要求とする。新要求には現在の権限、件数・容量上限、同時実行 1 件の採用契約を適用する。元 artifact の 7 日期限は新要求で延びず、新 artifact の期限と区別する。

生成中の部分失敗 manifest には成功対象と失敗対象を区別する。現在閲覧できない対象から本文・secret・私有 URL を取り出さない。既に保存済みの本人 job 最小 metadata と新たな note 読取を分ける。新しい回復要求の確認表示は、対象識別子 / 元の順番と理由だけでも対象を説明でき、失効対象の現在 title を取得する必要はない。

### 閲覧経路の変更と ticket

認可は「どこかで一度読めた」ではなく、その要求が使う現在の根拠で判定する。public URL から始めた匿名要求を private 化後の旧 ticket だけで継続しない。旧共有 token を再発行後の public 状態で迂回させず、EX-04 の旧リンク要求は not found とする。現在有効な public ページから操作をやり直すことは別の単体要求として許す。公開を読めることから匿名 / 閲覧者の一括 download 権限へ昇格させない。

サインイン済みの本人 job の status / 受取には本人認証を必須とし、含有 note の現在閲覧は独立した公開根拠も含めて評価する。EX-04 の旧 token 要求を拒否する条件と、完成済み本人 job に対して現在の公開閲覧を認める条件は別である。失効した membership そのものを認可の根拠に戻すことはしない。

password 変更は既存通過状態を失効させる。解除後は古い通過状態を認可に使わず、現在 password 不要の有効リンクから新しく操作できる。token 再発行、公開 URL 世代変更、trash、削除も、対応する古い入口の要求へ新しい認可を無言で付け替えない。ticket 再発行だけで古い閲覧資格を復活させない。

取得前の認可確認は、利用者が既に取得した bytes を回収する保証ではない。HTTP 応答途中の失効をどの粒度で停止できるかは配信実装の境界であり、本提案から無制限のストリーム監視や新しい期限を要求しない。

### 代案との比較

| 案 | 利用者への効果 / 判断 |
| --- | --- |
| 古い snapshot を現在認可だけで配る | 再取得は簡単だが、旧 private 本文を現在 public な note の artifact として渡し得るため不採用を推奨 |
| 内容不一致 / 一部失効の古い artifact を拒否し、明示した新要求へ案内（推奨） | 元 job と artifact が不変。更新後は一度の追加操作が要るが、同時実行制約・保持期限・取消との境界が明確 |
| 既存 ZIP を現在許可された subset で自動再構築 | 正当な兄弟を受け取りやすい。表示上同じ download でも内容・失敗一覧・期限が変わるため、新 artifact identity と進捗が必要。原文が必須とする回復方式ではない |
| PDF / ZIP を自動的に最新内容まで作り直す | 操作数は減るが、連続編集の追跡、取消、元要求の対象版、期限の扱いを追加で決める必要がある |
| app 利用者だけ旧 snapshot の再取得を許す | 元状態を再取得できるが、過去版の現在閲覧条件と export 固有の履歴保持を別に定義する必要がある。今回は追加しない |

PDF 24 時間・ZIP 7 日の未変更 artifact 再利用、job 90 日、匿名 PDF の ticket / 履歴外 / 一括不可は全案で維持する。1 GB の bytes 解釈、同時実行 1 件の主体、保持期限の起点など P4-prep の既存未決値は、本提案では解決済みにしない。
