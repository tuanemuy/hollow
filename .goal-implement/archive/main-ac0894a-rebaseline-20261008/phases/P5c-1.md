## 内向き型と責務

名前は新専用module内の候補。文字列ID・期限・版・sealed envelopeは境界VOで検証し、application内部は判別unionを使う。生tokenやprovider Responseをdomain/UIへ渡さない。

```ts
type DriveConnection = CommonConnection & (
  | { state: 'unlinked'; credential: null; folder: null }
  | { state: 'linked'; credential: VerifiedCredential; folder: FolderSetting }
  | { state: 'needs-relink'; credential: RetainedSealedCredential; folder: FolderSetting }
);
type FolderSetting =
  | { kind: 'unset' }
  | { kind: 'selected'; value: VerifiedFolder; checkedAt: Date };
type FolderObservation =
  | { kind: 'usable'; value: VerifiedFolder }
  | { kind: 'shortcut'; target: BoundedTargetReference }
  | { kind: 'trashed'; explicitly: boolean }
  | { kind: 'access-denied' }
  | { kind: 'unavailable-ambiguous' }
  | { kind: 'transient'; reason: 'rate' | 'provider' | 'network' }
  | { kind: 'invalid-metadata' };
type Owner =
  | { state: 'none' }
  | { state: 'active' | 'unknown'; runtimeGeneration: string; token: string }
  | { state: 'closed'; runtimeGeneration: string; token: string };
type DriveControlKind =
  | 'refresh' | 'picker' | 'folder-select' | 'folder-create' | 'disconnect';
```

CommonConnectionはaccountId、epoch、rowVersion、credentialVersion、settingsVersion、operationAdmissionSequence、connectedAt/lastUsedAt。autoBackupはこのphaseでliteral false。epochは採用/解除の境界、credentialVersionは通常refreshの交換、settingsVersionはfolder採用にだけ使い、無関係なlastUsed更新で毎回失効させない。FolderのID/name/driveId/resourceKeyは同じverified sub/epochに束縛する。subは255文字の公開OIDC上限に従い、emailは任意の表示情報とする。

attemptは `pending(verifier+nonce) → exchanging(owner) → candidate(sealed token set) → completed`、又は `failed/cancelled/expired`。交換不明はfailedの有限理由とowner unknownを分ける。candidate以降にコードを再交換しない。operationはkindごとの固有payloadと `queued/running/awaiting-selection/ready/reconciling/completed/failed/cancelled` を合法な組合せだけで表す。全kindで全stateを許す巨大nullable DTOにはしない。

主port候補:

- `DriveConnectionRepository`: find/ensure、adoptCandidate(expectedEpoch, credentialVersion, settingsVersion, admission)、replaceCredential、selectFolder、disconnect。専用CASでのみimmutable bindingを変える。
- `DriveAuthorizationAttemptRepository`: actor+command一回受付、stateHash検索、一回exchange claim、candidate保存/採用、cancel、限定prune。
- `DriveControlRepository`: actor+command receipt、同accountのattemptを含むowner admission、kind別claim、phase CAS、cancel generation、closed proof、有限history/prune。外部要求をTx内で実行しない。
- `DriveAuthorization`: authorization、exchange、verifyCandidate、refresh。結果は検証済identity/grants/期限と短命の内部secretだけ。専用HTTPを使いSDKの自動再送は無効、claims検証だけ既依存google-auth-libraryを使用する案。
- `DriveFolderProvider`: generateFolderId、inspectFolder、createFolder。任意URL、list全探索、media、delete/trash/revokeをportに作らない。
- `DriveSecretProtector`: verifier/candidate/credential/resource-keyのpurpose別AAD。Drive専用keyringでaccount/attempt又はsub+epoch+credentialVersionを束縛する。
- `DriveExecution`: claim済owner tokenを受けて `result` と `closed` を別に返す。abort/timeout/errorはclosedの代用でない。stopは全既知request/response/socketの実終了を待つ。

既 `auth/googleHttp.ts` は固定token/certificates endpointと実close、`openrouter/execution.ts` はin-memory枠である。構造参考に限り、Driveによる既Google/OAuth/LLMのendpoint union・pool・秘密purpose拡張は行わない。新Drive runtime ownershipを専用に設け、既execution/runtimeOwnershipは不変更案。

## 認可・refresh・現在fence

1. begin POSTで現在verified本人、sessionHash/authVersion、browser世代、connection epoch、settingsVersionと操作確認集合を保存。SSOの検証済subはlogin_hintの助言だけ。同じaccountを強制せず「別のGoogleアカウント」を提供する。Hollow session/Google Identityの発行・交換はしない。
2. 候補scopeは `openid email drive.file`、profile/drive/drive.readonly/metadata.readonlyは要求しない。emailはIN-08表示向け任意、欠落でsubをメールに置換しない。offline、incremental、state、nonce、S256、固定callback。既projectのcombined権限は追加scope要求と別に観測し、専用downscopeと称さない。
3. callback GETはOAuth応答を消費する明示例外で、通常receipt/settings GETとは別。queryの重複/長さ/state/browser/currentを確認後、一回CAS→Tx外exchange→検証候補暗号化保存→current再照合→採用。303でqueryなし結果画面へ、no-store/no-referrer/noindex、callback query/Locationをログにしない。cancel/state不一致は別attemptへ割り当てない。
4. 署名/issuer/aud/azp/nonce/iat/exp/subと必要grantsを検証する。利用可能ならat_hashも照合する。scope不明を許可済み扱いしない。初回/明示再連携でrefresh不足なら新consentを利用者に促す。失敗しても旧有効connectionを先に破棄しない。provider側で旧tokenが失効しない保証ではない。
5. exchange intent後の応答不明は自動再交換0。candidate保存済みなら同candidateの検証/採用だけ再開可能。JWT検証時の証明書GETも同owner内で有限にし、requestごと実closeする。unknown所有のまま新exchangeを開始しない。
6. 通常refreshは明示再連携ではない。現在sub/epoch/credentialVersionでsingle-flight、応答に新refreshがなければ同版の旧値保持、新値ありなら暗号化差替え。遅い401/invalid_grantはその版だけをneeds-relinkへし、新採用済み接続には作用しない。refresh送信後の応答不明ではrotation喪失の可能性を残し、自動反復0、close確認後に再連携を案内する。not-sentを実証した一時失敗だけ、明示再開を許す。
7. 明示再連携の開始は現在folder operationのID集合/admissionと影響説明の確認を要する。新folder操作が増えれば再確認。新候補検証成功時の採用Txで旧epochをfence・旧folder操作のcancel intent・新credential採用を一括確定し、実closeは別に待つ。旧unknownがあれば採用を待機する。別subへ旧folderを付け替えない。同subでも新epochで再検査し、利用者へ提示して再採用する。backup取消の未回答をこの契約から決定しない。

純GETはsession/account/browserの既値を読み、期限/current差はprojectionだけで返す。既 `captureAuthentication` はlegacy browser bindingを書き得るため、そのまま純GETで呼ばない。begin POST側だけ既captureを利用し、Driveのread-only current関数は既repository読取で比較する。GETでrefresh/ensure/prune/wake/cancelやprovider GETも行わない。

## 保存先・Picker・作成のprotocol

### Pickerと候補採用

`issuePicker POST(actor+command, expectedEpoch/settingsVersion)` → operation receipt作成 → 必要なrefreshを同ownerのsubstepで完了 → no-storeの専用応答にaccess token/実期限/5分local ticketを一回渡す。tokenはReact stateの通常DTO/cache/SSRへ載せず、Picker controllerのclosureだけ。ACK不明のreceipt GETは資格を再配布せず、明示再開POSTを要する。再発行は新tokenの発行数に数え、無限mintしない。

通常folder用DocsViewとsharedDrive専用DocsViewを用意し、upload viewなし。選択callbackからはID/keyだけを送る。URL/name/MIME/account表示は採用根拠でない。serverは同sub credentialで固定metadata GETを実行し、id一致・folder MIME・非trash・canAddChildren・settings/currentを前後照合してCAS採用。共有DriveはdriveIdを保持し、owners/ownedByMe必須にしない。folderを選べてもその全子fileにdrive.file権限があるとは表示しない。

shortcut選択は別結果として返す。server取得のtargetId/targetResourceKeyを使う単段の実体確認は可能だが、その実体を選ぶ確認POSTを別に挟む。実体を同credentialで検証できない場合はPickerで実体を再選択してもらい、権限を推測しない。連鎖/循環/別種/不正metadataは有限拒否。黙った追跡・名前一致による代替なし。この明示target確認を最小support案としてManagerへ返す。

保存済folderの再確認も明示POSTでoperation化する。`trashed` は再選択/復元を案内、`unavailable-ambiguous` は「見つからないかアクセスできない」、403はreasonを有限分類しrateと権限を分ける。通信失敗で設定を空にせず、最後の確認日時と今回failureを分ける。remoteの検査直後に権限が変わる分散競合は避けられず、後段実backupでも再検証する。

### 既定専用folder

初回連携成功後に既定候補「専用フォルダを作成」を提示し、IN-05の保存操作で開始する。認可callback/設定GETだけで作成しない。新規作成の既定は同Google本人My Driveのroot。共有Driveは既存folder選択で対応し、その保存先内への将来backupをP5c-2へ残す。

作成requestでparentsを省略するとMy Drive直下に置かれるのは[公式folder説明](https://developers.google.com/workspace/drive/api/guides/folder)の契約。ただし応答喪失後にも同位置にあることを保証しない。新scopeによるroot探索はしない。

1. `folder-create` operation/command/current/設定版を永続化。
2. Tx外 `files.generateIds(count=1, space=drive, type=files)`。受領IDを同operationへCAS保存してからcreate intent。ID応答喪失時点ではfolder送信0なので実close後の明示再開でID取得し直せるが、create intent以後はIDを固定する。
3. `files.create` はmetadataのみ、保存済ID・固定folder MIME・専用表示名・opaque operation markerのappProperties。任意parent/任意URLなし。成功応答でもid/metadataを確認して現在fenceの下で採用。
4. create応答不明では同command GETは状態読取だけ。明示「結果を確認」POSTで同ID metadata照会し、同sub credential、id/MIME/nontrash/canAddChildren/作成markerを確認する。保存済みparent観測があれば一致も要求する。parent未観測なら「現在もMy Drive直下」とは断定せず、照合できた現在folder候補の明示確認を経て採用する。409もこの照合を省略しない。名前一致だけでは採用しない。
5. metadata404は曖昧なまま。利用者が同operationを明示再開する場合だけ同じ事前IDのcreateを最大1回再送する候補（初回と合計2）。新IDへ自動交換0、409照会失敗なら不明保持。後段でさらに必要なら別判断とし、retryを無制限にしない。
6. cancel/epoch変更後のremote成功は設定へ採用しない。Google側にfolderだけ成立した可能性を安全historyに残す。自動delete/rollbackはしない。旧backup bindingは変更しない。

`appProperties` の作成markerは認可の代用ではなく同operation照合の補助。既存folder選択には要求しない。旧subのfolderを新subで「同一作成」と採用しない。

## 有限HTTP・実所有・解除

候補値はHTTP1本10秒、1operation30秒＋close猶予5秒、metadata/token64KiB、証明書256KiB、request body16KiB。status/header/JSONも有限、Content-Encoding identity、redirect0、agent poolingなし。固定token/certificates/Drive generateIds/get/createだけを許可し、Drive RESTはprojection fieldsを固定する。provider quotaの上限保証ではない。boundedな429/5xxは明示再開案内、token/code/createの自動retryはしない。

専用Node runnerはleaseと物理所有を分離する。request/response/socketのcloseを全部待ち、期限だけならowner unknownへ残す。新プロセスは専用runtime generation/排他lockと既所有者実終了証拠を照合し、PID数値だけやheartbeat期限でclosedを捏造しない。分からなければ起動後のDrive受付を閉じたままにし、他のHollow機能は継続する。forcekill/任意PID探索を回復手順にしない。

disconnect確認POSTはcommand idempotent。同Txでepoch増加、credential/candidate/verifier/resource-key破棄、auto=false、旧attempt/operationへcancel intentを付ける。現在UIは未連携＋停止処理中を区別し、遅い採用を拒否。abort後も実closeまでowner/runtime枠を保持し、元request内メモリに残るsecretが即消えたとは保証しない。account/Google Identity/session・OpenRouter/LLMには触れない。Google revoke/delete/trashは呼ばない。既browser tokenはprovider期限まで使われ得る限界を明示する。

logout/actor変更ではUIのpending owner/generationを失効しPicker/token参照を破棄。serverは各外部step前/結果Txでsession/browser/authVersionを再確認し、runnerも失効を検出してcancelする。送信済外部効果まで取消済みとはしない。通常route離脱だけでdurable操作を作り直さず、再訪は同receiptを読む。unknown/取消は再POSTへ自動変換しない。

## UI・配備・秘密境界
