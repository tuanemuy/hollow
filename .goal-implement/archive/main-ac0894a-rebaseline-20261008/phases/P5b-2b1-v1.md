## 原因と最小差

`documentOffice.mjs` のPPTX `addSlide` 内paragraphは全子孫の `a:t` を `texts()` で集め `join("")` する（471〜474行）。`preserveOrder:true` のXML木には順序があるが、抽出時に `a:br` を落としている。`sameText()` は `a:t` 列しか比較しないので構造欠落を検出しない。`documentBlocks.mjs` の `textBlocks()` は既に改行文字を `<br>` へ安全に変換するため、共通serializerの変更は不要。

推奨する修正範囲はPPTXだけの順序付きinline抽出。各paragraphでXML文書順に `text(value)` と `line-break` の有限列を取得し、文字は無変更・run境界では何も挿入せず、明示 `a:br` だけを改行1個として `textBlocks` に渡す。先頭/末尾/連続の `a:br` をtrimやcollapseせず、`<p><br>A<br><br>B<br></p>` のように保持する。複数 `a:r` の隣接 `a:t` は従来通り連続する。段落は従来通り別 `<p>`、明示改行を別paragraphに変えない。文字なし文書は既NO_TEXTのまま、改行だけで新たに成功させない。

抽出対象のtextとbreakを同じ順序で消費したことをPPTX専用inventoryで照合する。未知の本文構造に遭遇して扱えない場合は既 `LLM_DOCUMENT_UNSUPPORTED` で失敗させ、文字がないからといって意味のある未対応境界を成功として捨てない。書式metadataの網羅的仕様追加や全DrawingML対応には拡張しない。既supported run/fieldの表示文字は無断で削らず、XML値の空白・改行・Unicodeをそのまま保持する。

同じPPTX table cellにも `texts(a:tc, a:t).join("")`（481〜493行）があり、paragraph/改行を消す同根の経路がある。ここも同じinline抽出を再用する狭いB修正を提案する。単一paragraph・改行なしの旧 `<td>表</td>` はbyte不変とし、単一paragraph内の改行だけ `<br>`、複数paragraphは各 `<p>` で区別する。cellを複数table/blockへ分割しない。既巨大table64KiB拒否を維持する。空paragraph/連続空paragraphも明示境界を保持する必要があるため、複数paragraphの場合だけ空 `<p></p>` を含める。未知のtable構造を新規対応する変更ではない。この同根table経路を含める採否はManagerへ返す。
